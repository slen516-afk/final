## 二、各頁內容規劃與亮點

### 第 1 頁：資料庫規劃與建置 — 技術選型與架構

**報告重點**

- **為何選 PostgreSQL（Supabase）而非 MySQL**
  - 專案採用 **Supabase（底層 PostgreSQL）**，與學過的 MySQL 的取捨可簡述為：
    - **JSONB 支援**：職缺 `job_details`、問卷 `career_preference`、履歷 `structured_data` 等大量使用 JSON/JSONB，PostgreSQL 的 JSONB 查詢與 GIN 索引較適合。
    - **與 Supabase 生態整合**：Auth、Storage、Realtime、Row Level Security 一體，方便前後端與廠商展示。
    - **向量擴展**：若未來要在 DB 內做 pgvector，PostgreSQL 原生支援；目前採「PostgreSQL + Qdrant」雙軌，架構一致。
  - **一句話**：結構化資料需要強型別 + JSON 彈性 + 雲端服務整合，故選 Postgres（Supabase）。

- **雙軌儲存架構（必講亮點）**
  - **Supabase (PostgreSQL)**：所有結構化資料（帳號、職缺、履歷、問卷、技能、媒合結果等），共 **24 張表**，欄位對齊 ERD。
  - **Qdrant Cloud (Vector DB)**：語意搜尋用向量，透過 **`vector_id` (UUID)** 與 Supabase 關聯。
  - 口頭可說：「先入庫拿 ID，再同步到 Qdrant，回寫 `vector_id`、`is_embedded`，狀態單一來源在 Supabase。」

**值得放進簡報的內容**

- 一句話技術選型理由（Postgres vs MySQL）。
- 雙軌架構示意：`Supabase（結構化）↔ vector_id ↔ Qdrant（向量）`。

**建議截圖／圖**

- 組長提供的「數據存儲」投影片右側 **Supabase Schema 簡圖** 位置，可補上一張 **雙軌架構示意圖**（左：Supabase 表名列表；右：Qdrant collections：`job_vectors`, `resume_vectors`, `optimized_resume_vectors`）。

**對應程式／文件**

### 第 3 頁：資料清洗原則與流程

**報告重點**

- **資料清洗如何做**：依 `cleaner步驟_v2.md`，職缺從 **jobs_rows.csv（104 爬蟲）** 到寫入 **company_info、job_posting、job_skill_requirement**，共 **九階段**；可簡化成「探索 → 清理函數 → 公司／職缺清理 → 驗證 → 寫入 → 技能需求與未匹配匯出」。
- **清洗原則簡述**（對應「數據清整原則簡述」）：
  - **文字**：`clean_text` 去多餘空白、換行、特殊字元。
  - **公司**：`clean_company_name`、依公司名稱與職缺類別推斷 **industry**（如資訊科技、金融、醫療）。
  - **地點**：`standardize_location` 產出 **full_address / city / district**，供寫入與後續篩選。
  - **薪資**：`clean_salary`，待遇面議統一為 40000/40000；區間拆成 **salary_min / salary_max**。
  - **遠端**：`determine_remote_option` → remote / hybrid / onsite。
  - **職缺要求**：`merge_requirements` 合併 work_exp、education、skills、tools 等為單一 **requirements**；**job_details** 用 JSON 存福利等。
  - **去重**：有 `source_url` 時依 **source_url + update_date** 留最新一筆（Upsert）；無則依 (company_name, job_title, full_address) 去重。
  - **技能**：從 skills/tools 解析後對 **skill_master** 做同義詞匹配，未匹配匯出 **unmatched_skills.csv** 供後續補表。

**值得放進簡報的內容**

- 九階段流程簡表（或合併成 4～5 個大步驟）。
- 上述「清理原則」列點（文字／公司／地點／薪資／遠端／要求／去重／技能）。

**建議截圖／圖**

- **Data Pipeline 流程圖**（組長表內「補 Data Pipeline 流程圖」）：從 104 爬蟲 → jobs_rows.csv → 清理腳本 → company_info + job_posting + job_skill_requirement（+ unmatched_skills.csv）。
- 程式碼截圖 1～2 張：例如 `scripts/jobs/job_clean_and_upload.py` 中的 **清理函數呼叫順序** 或 **寫入 Supabase 的迴圈**，展現與文件一致。

**對應程式／文件**

- `docs/cleaning/cleaner步驟_v2.md`（九階段完整）
- `scripts/jobs/job_clean_and_upload.py`（職缺清洗與寫入）

### 第 4 頁：清洗前後對比與品質驗證

**報告重點**

- **是否有清洗前後對比**：組長備註「待確認」— 你已有 **階段五：資料驗證與統計** 與 **階段八：匯出清理後備份**，可視為「前後」的數據基礎。
- **建議做法**：
  - **數量對比**：原始 `jobs_rows.csv` 筆數 vs 去重後職缺數 vs 寫入 `job_posting` 筆數；公司數、有 industry 的公司數。
  - **品質對比**：清理前缺失值／重複數 vs 清理後；有 salary_min/max、full_address、requirements 的筆數與比例。
  - **技能**：匹配率（寫入 job_skill_requirement 的筆數 vs 未匹配技能數／unmatched_skills.csv 筆數）。

**值得放進簡報的內容**

- 一張「清洗前 vs 清洗後」對照表（欄位：筆數、缺失率、重複數、關鍵欄位完整率等）。
- 若曾跑過腳本：實際數字（例如「原始 12,000 筆 → 去重後 9,500 筆 → 寫入 9,200 筆」）會很有說服力。

**建議截圖／圖**

- **表格**：清洗前 / 清洗後 關鍵指標（筆數、缺失、重複、完整率）。
- 可選：**Supabase Table Editor** 中 `job_posting` 前幾筆，顯示 **salary_min/max、full_address、city、district、remote_option** 已填滿的樣貌；或 **unmatched_skills.csv** 在 Excel 中開啟的畫面（說明未匹配技能的後續處理）。

**對應程式／文件**

- `docs/cleaning/cleaner步驟_v2.md` 階段五（驗證與統計）、階段八（匯出備份）

### 第 5 頁：向量化流程與回寫機制

**報告重點**

- **向量化哪些欄位**：職缺以 **job_title + job_description + requirements** 合併成一段文字，截斷至 8000 字元後送 **OpenAI text-embedding-3-large（1536 維）**；履歷、優化履歷同理，對應 **resume**、**resume_optimization** 的結構化內容。
- **對應向量資料庫**：Qdrant 三 collection — **job_vectors**、**resume_vectors**、**optimized_resume_vectors**。
- **完成後回寫**（重要亮點）：
  - 從 Supabase 取 **is_embedded = FALSE** 的資料 → 呼叫 OpenAI 取得向量 → 寫入 Qdrant（含 **payload**：job_id、city、district、remote_option、salary_min、salary_max 等硬篩選欄位）→ 取得 Qdrant 的 **point id (UUID)** → **回寫 Supabase**：`UPDATE job_posting SET vector_id = ?, is_embedded = TRUE WHERE job_id = ?`。
  - 履歷、優化履歷同理；**resume_optimization** 需先執行 `migrations/add_resume_optimization_vector_columns.sql` 新增 **vector_id、is_embedded**。

**值得放進簡報的內容**

- 四階段流程：**Phase 1 提取（Supabase）→ Phase 2 向量化（OpenAI）→ Phase 3 寫入 Qdrant（含 payload）→ Phase 4 回寫 Supabase（vector_id, is_embedded）**。
- Payload 含硬篩選欄位（地區、遠端、薪資範圍），方便搜尋時先篩再做語意檢索。
- 驗證方式：**verify_sync.py** 比對 Supabase 已嵌入筆數與 Qdrant points_count，並抽查 vector_id 與 payload。

**建議截圖／圖**

- **向量化流程圖**：可直接用 `docs/vectorization/career_pilot_vectorization_guide.md` 內的 **ASCII 四階段架構圖** 擷圖或重繪。
- **verify_sync.py 執行結果**：Supabase 已向量化筆數 = Qdrant 向量總數、抽查 2～3 筆 job_id / vector_id / 薪資 一致。
- 可選：**Supabase** 中 `job_posting` 一筆的 **vector_id、is_embedded** 欄位；或 **Qdrant** 單一 point 的 payload 畫面（若有權限）。

**對應程式／文件**

- `docs/vectorization/career_pilot_vectorization_guide.md`（四階段、欄位對應、薪資篩選邏輯）
- `scripts/vectorize_jobs.py`、`scripts/vectorize_resumes.py`、`scripts/vectorize_optimized_resumes.py`
- `scripts/verify_sync.py`
- `migrations/add_resume_optimization_vector_columns.sql`
- `scripts/qdrant/setup_collections.py`（1536 維、COSINE、collection 名稱）

## 三、你還可以加分的亮點（選講）

- **職缺寫入策略**：有 **source_url** 時用 **Upsert（on_conflict=source_url）** 更新同一職缺最新版，無則以 (company_id, job_title, full_address) 防重複。
- **技能同義詞與未匹配處理**：skill_master 的 **synonyms** 建反向索引做匹配；未匹配寫 **unmatched_skills.csv**，可提「後續可接 LLM 分類或手動補表」。
- **薪資篩選邏輯**：Qdrant payload 存 **salary_min / salary_max**，搜尋時用「salary_min ≤ 期望薪資 ≤ salary_max」做硬篩，再語意排序，避免先取回大量向量再過濾。
- **Coursera 課程資料**：若時間允許可一句話帶過：另有課程清洗與寫入 **course** 表，邏輯見 `coursera_cleaning_steps.md`。
- **問卷／履歷寫入 API**：`db_function/db_writes.py` 提供問卷、履歷、上傳、技能、求職信等寫入，給後端呼叫，可說明「資料庫與應用層分工」。

## 五、報告內容流程（口頭順序建議）

1. **開場**：負責「資料工程層」的資料庫部分，包含規劃建置、清洗、向量化與回寫。
2. **技術選型**：為何用 Postgres（Supabase）與雙軌架構（結構化 + 向量），一句話帶過 MySQL 取捨。
3. **ERD**：核心表與關聯、寫入順序，配合 Schema 簡圖。
4. **清洗**：資料來源（104）、九階段簡化為原則與流程，配合 Data Pipeline 圖；若有數字再講清洗前後對比。
5. **向量化與回寫**：哪些欄位、四階段、回寫 vector_id / is_embedded，以及驗證方式。
6. **收尾**：可提後續（如搜尋 API 硬篩 + 語意、未匹配技能補充、課程資料等）。
