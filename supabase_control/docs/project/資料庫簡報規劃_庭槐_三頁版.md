## 【第 1 頁】雙軌架構與技術選型（1.5 分鐘）

### 投影片內容建議（精簡條列）

- **這頁要解決的問題**：資料進到系統後，結構化資料和語意搜尋資料分別放哪裡、為什麼要用雙軌架構。
- **雙軌示意圖（核心視覺）**  
  - 左側：`Supabase / PostgreSQL`，標註「結構化資料、24 張表、單一真實來源」。  
  - 右側：`Qdrant`，標註「向量資料庫、3 collections：job_vectors / resume_vectors / optimized_resume_vectors」。  
  - 中間用 `vector_id` 箭頭串接，補註「Supabase 記錄向量狀態 is_embedded」。  
- **技術選型一句話**  
  - 原本也會想到 MySQL，但專案更依賴 **JSONB 欄位** 和 **Supabase 一整套生態系整合**，因此選擇 PostgreSQL + Supabase。  
- **JSONB 的實際用途**  
  - 職缺的 `job_details`、履歷的 `structured_data`、問卷偏好等，內容結構變動多，用 JSONB 存起來，查詢時可以只撈裡面需要的欄位。  
  - 搭配索引之後，仍然維持可查詢、可過濾的效能。  
- **Supabase 生態整合**  
  - 同一套服務提供 Auth、Storage、Row Level Security，前後端只要面對一個入口。  
  - 實際系統中，所有表都在 Supabase 這一邊維護，所以它是真實來源，Qdrant 只存「搜尋用向量」。  
- **雙軌分工邏輯**  
  - **Supabase**：負責「誰是誰、欄位是什麼」——帳號、公司、職缺、履歷、問卷、媒合結果都在這裡，資料乾淨、關聯清楚。  
  - **Qdrant**：負責「誰跟誰像」——只存 embedding 向量，加上幾個硬篩欄位（地點、薪資、是否遠端）放在 payload。  
  - 兩邊透過 `vector_id` + `is_embedded` 狀態欄位同步，查詢時先問 Supabase 要哪一群，再讓 Qdrant 幫忙算「最像的幾個」。  

### 口頭稿（約 1.5 分鐘）

這一頁要處理的事情是，讓評審很快理解資料進來之後，落在哪兩個系統、各自負責什麼。  
整個專案的真實來源放在 Supabase，也就是底層的 PostgreSQL，我們把 24 張結構化表都規劃在這邊，包含公司、職缺、履歷、問卷到媒合結果。  
有些欄位像職缺詳細描述、履歷解析結果，結構本身變動很大，所以我不是拆成一百個 column，而是放進 JSONB 欄位裡，查詢時只拿需要的部分，這樣既保留彈性，也不會把 schema 弄得太破碎。  
選 PostgreSQL 而不是 MySQL，是因為這些 JSONB 用得很重，再加上 Supabase 幫我把 Auth、Storage、權限控管都打包好，對專題來說整合成本更低。  
另一側的 Qdrant 扮演的角色比較單純，它只存 embedding 向量和幾個關鍵欄位，例如薪資區間、城市和遠端選項，這些會被放到 payload 裡，用來硬篩。  
在中間用 `vector_id` 串起來，實作上就是資料先寫進 Supabase，拿到主鍵之後，再去做向量化，寫進 Qdrant，最後把產生出來的向量 ID 回寫到原本那一筆職缺或履歷上。  
這樣設計的好處是，系統裡「這個職缺到底有沒有被向量化過」只看 Supabase 的 `is_embedded` 欄位就知道，Qdrant 只專心提供語意搜尋，兩邊分工清楚。  
後面幾頁會從這個雙軌架構往下展開，說明資料怎麼被清洗乾淨，還有向量化和驗證的流程。  

### 建議截圖／視覺佔位符

- **雙軌架構圖佔位符**：  
  - 左：`Supabase（24 tables, JSONB）`  
  - 右：`Qdrant（job_vectors / resume_vectors / optimized_resume_vectors）`  
  - 中間：`vector_id` 箭頭 + `is_embedded` 狀態標註。  
- **JSONB 欄位示意截圖**：Supabase 後台顯示 `job_details` 或 `structured_data` JSONB 欄位展開畫面。

## 【第 2 頁】資料清洗流程與品質驗證（2 分鐘）

### 投影片內容建議（精簡條列）

- **這頁要解決的問題**：原始爬回來的職缺資料品質參差不齊，要如何清成可以直接給演算法和評審用的等級。  
- **四框流程圖（核心視覺）**  
  - 框一：`CSV 原始資料`（例：jobs_rows.csv，含職缺文字、地點、薪資等原始欄位）。  
  - 框二：`清洗（文字 / 地點 / 薪資 / 去重）`，標註「九階段實作，這裡收斂成四大類清洗」。  
  - 框三：`寫入 DB`，指向 Supabase 的 `company_info`、`job_posting`、`job_skill_requirement` 等表。  
  - 框四：`驗證輸出`，包含統計檢查與清洗後備份。  
- **四大清洗邏輯（不展開九階段細節）**  
  - 文字與欄位整理：統一字串格式、拆出城市與行政區、將面議薪資轉成可比較的區間。  
  - 公司與產業歸類：整理公司名稱、依職缺與公司特徵推論 industry，避免同一家公司被拆成多種寫法。  
  - 薪資與遠端欄位：把文字描述轉成 `salary_min` / `salary_max` 和 `remote_option`，方便後續硬篩。  
  - 去重與寫入：利用 `source_url` 或公司名加職稱等條件去重，只留下最新且內容完整的一筆，再寫入資料庫。

| 有薪資區間比例           | [X]%         | [X]%         |

### 口頭稿（約 2 分鐘）

這一頁聚焦在一件事，就是讓大家放心，爬回來那些有缺字、有錯別字、薪資寫「面議」的職缺，最後會被整理成可以直接用來訓練和搜尋的乾淨資料。  
原始來源會先進到 CSV，裡面包含公司名稱、職稱、工作內容、地點文字、薪資描述等等，品質其實蠻不一致，像同一家公司可能有三種寫法，地點有時候只有「台北市」，有時候帶整串地址。  
清洗階段在實作上切成九小步，簡報裡我把它濃縮成四大塊來看：一塊是把各種文字欄位做標準化，把多餘空白、奇怪符號處理掉；一塊是針對地點，把完整地址拆成城市和行政區，讓之後查詢或硬篩比較容易。  
第三塊是薪資與遠端欄位，像「待遇面議」這種，在系統裡會轉成一個可比較的區間，順便補上 `salary_min`、`salary_max`，同時也把是否遠端、混合或純實體整理成一個欄位。  
最後一塊是去重和寫入，如果爬蟲多次抓到同一個 `source_url`，就只保留更新日期比較新的那一筆，避免統計被重複職缺灌水。沒有網址的情況，會用公司名稱、職稱和地址組成條件，盡量挑出最合理的一份。  
清洗完之後，我會先寫入 Supabase 的幾張核心表，並且跑一個驗證步驟，把清洗前後的筆數、薪資欄位的填寫比例、還有產業分類的正確率統計出來，像表格裡可以看到 industry 分類修正到大約八成以上。  
等實際跑完腳本，我會把這些 [X] 數字補上，讓評審在一眼之內就看得出來，清洗不是只有概念，而是真的有改善資料品質。

- **清洗前後對比表佔位符**：如上表格，以實際執行結果填入 [X]。  
- **Supabase 表內容截圖**：`job_posting` 與 `company_info` 範例列，顯示地點、薪資、industry 已填寫完成。

## 【第 3 頁】向量化流程與回寫驗證（2 分鐘）

### 投影片內容建議（精簡條列）

- **這頁要解決的問題**：清洗過的結構化資料，要怎麼變成可搜尋的向量，並確定 Supabase 和 Qdrant 兩邊沒有不同步。  
- **四步驟垂直流程（核心視覺）**  
  1. `Supabase 取出 is_embedded = FALSE`  
     - 從 `job_posting`、`resume` 或 `resume_optimization` 撈出還沒向量化的紀錄，包含文字內容與硬篩欄位。  
  2. `OpenAI Embedding API（text-embedding-3-large）`  
     - 將職缺標題、描述、需求等文字組合成一段 context，呼叫 Embedding API 產生 1536 維向量。  
  3. `寫入 Qdrant（payload 含薪資 / 地點 / 遠端）`  
     - 將向量與 payload 一起寫入對應的 collection（job_vectors / resume_vectors / optimized_resume_vectors）。  
  4. `回寫 Supabase（vector_id + is_embedded = TRUE）`  
     - 取得 Qdrant point 的 `id`，更新回原本那一筆資料的 `vector_id`，並把 `is_embedded` 改成 TRUE。  
- **payload 硬篩邏輯**  
  - payload 中至少包含 `city`、`district`、`remote_option`、`salary_min`、`salary_max` 等欄位。  
  - 搜尋時先用這些欄位做條件過濾，例如限定目標城市或可遠端、薪資要落在某個區間，再在符合條件的向量上做語意排序。  
  - 這樣可以減少不相關的職缺被拿來算距離，同時讓搜尋結果更貼近使用者實際條件。  
- **回寫與驗證機制簡述**  
  - Supabase 保留 `is_embedded` 狀態以便續跑，避免重複向量化。  
  - `verify_sync.py` 用來比對 Supabase 與 Qdrant 的筆數和 sample payload，確認兩邊資料一致。  

### 口頭稿（約 2 分鐘）

這一頁想解釋的是，當資料已經在 Supabase 清洗好之後，怎麼變成可以做語意搜尋的向量，還有我要怎麼確認中間沒有漏寫或對不上。  
流程從 Supabase 開始，我會撈出 `is_embedded = FALSE` 的紀錄，這樣腳本在重複執行的時候，不會一再處理同一筆資料，也方便未來補量或重新向量化。  
對每一筆職缺，系統會把職稱、工作內容、條件需求這幾個欄位組合成一大段文字，送進 OpenAI 的 `text-embedding-3-large` 模型，產生一個 1536 維的向量。履歷和優化後履歷的做法類似，只是文字來源換成候選人的經歷和技能描述。  
拿到向量之後，我會把它寫進 Qdrant 對應的 collection，同時把薪資上下限、城市、行政區、是否遠端等欄位放進 payload。這些欄位在搜尋時會先被用來做硬篩，像是只看台北市、只看薪資高於某個門檻、只看可以遠端的職缺。  
硬篩完之後，才在符合條件的那一小群向量裡做語意排序，這樣既省計算，又能讓排序結果比較符合使用者心中真正想找的職缺或履歷。  
每一筆成功寫入 Qdrant 後，會拿到一個 point id，我會把這個 id 回寫到 Supabase 對應那一筆資料的 `vector_id` 欄位，並且把 `is_embedded` 標記為 TRUE，方便之後直接用資料庫判斷完成度。  
為了避免兩邊數量慢慢跑偏，我有寫一支 `verify_sync.py` 腳本，定期檢查 Supabase 裡 `is_embedded = TRUE` 的筆數跟 Qdrant 的向量數是否一致，並抽幾筆比對 payload 裡的薪資和地點，確保搜尋底層是對得起來的。  

### 建議截圖／視覺佔位符

- **四步驟垂直流程圖佔位符**：  
  `① Supabase 取 is_embedded = FALSE → ② OpenAI Embedding API（text-embedding-3-large） → ③ 寫入 Qdrant（payload 含薪資 / 地點 / 遠端） → ④ 回寫 Supabase（vector_id + is_embedded = TRUE）`。  
- **Qdrant payload 示意截圖**：展示單一向量點的 city、district、remote_option、salary_min、salary_max。  
- **verify_sync.py 執行結果截圖佔位符**：終端機輸出顯示 Supabase 和 Qdrant 筆數一致，並列出數筆對照 sample。

## 選講（加分，可視時間斟酌）

- **skill_master 同義詞匹配邏輯（選講）**  
  - skill_master 中事先整理多種寫法與同義詞，產生反向索引，清洗時只要命中其中一個別名，就能對應回主技能。  
  - 這樣可以吸收像「前端工程師 / Frontend Engineer / Web Engineer」這種寫法差異，提升技能標記的穩定度。  
- **Upsert 寫入策略：source_url 去重（選講）**  
  - 寫入職缺時，若有 `source_url`，會用 Upsert 方式以它為唯一鍵，保證同一份職缺只保留最新的一版。  
  - 沒有網址的情況，則退而求其次用公司、職稱與地址組合作為去重條件。  
- **unmatched_skills.csv 後續處理（選講）**  
  - 清洗過程中無法對應到 skill_master 的技能會被寫到 `unmatched_skills.csv`，後續可以人工檢視或交給 LLM 幫忙做建議分類，再回填到主表。  
- **Coursera 課程資料一句帶過（選講）**  
  - 課程資料沿用相同清洗與寫入原則，落在獨立的 course 表，供後續做職涯建議與學習路徑推薦。
